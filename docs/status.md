## What this project is

The **1 Bitty Challenge**: a small group each put up to 1 BTC into a basket of 2 to 8 alts, sell near the top,
rebuy BTC in the bear, and are scored in BTC. A Next.js 16 app on Vercel and Supabase, plus a Python engine
that refreshes market data daily. Live at https://rotation-web-seven.vercel.app. Repo: `mattpmerrill/rotation`
(public; the owner decided on 2026-09-30 to leave it public as it is and not rewrite history).

It is also a showcase of a written set of engineering standards (see
[ADR-001](decisions/ADR-001-adopt-engineering-standards.md)) applied to a small real app. That is why so much
of the work is guards, tests and docs.

- The daily job (GitHub Actions, 13:15 UTC) refreshes market data; the app's notification job posts to
  Discord **only once `DISCORD_WEBHOOK_URL` is set in Vercel (it is not, yet)**.

## The showcase cleanup (in production since 2026-09-30)

No migration and no database type changed, so there was nothing to apply to production first:

- **Layers.** A new `web/src/integrations/` layer with one adapter per vendor (`coingecko`, `discord`); only
  features import it. Files in `data/` that build queries are `<thing>.repository.ts`, the access guards are
  `data/guards.ts`, and routes reach the session through `features/auth/viewer`. `app` and `proxy.ts` can no
  longer import `data` or `integrations` (ESLint and dependency-cruiser). Logic that sat in pages and route

- **Validation.** CoinGecko's response and the engine's three JSON files are parsed with zod; casts that had
  no reason are gone. Exceptions 4 and 5 are retired.
- **Security headers.** A nonce-based CSP built per request in `src/proxy.ts`, static headers in
  `next.config.ts`, every page rendered per request, and an e2e spec for the headers. Exception 10 is retired.
  This has been verified against a local production build only.
- **Dead code.** The two unreferenced CoinGecko client methods, a dead config field and the 17 unused
  `rules.yaml` sections (now version 2, with their config models) are removed (exception 16; only two unused
  tables remain).
- **Demo data.** `supabase/seed.sql` (generated by `supabase/seed/build_seed.py`) gives `supabase db reset` a
  full demo challenge with invented people, and `npm run screenshots` retakes the README images. Exception
  18 is retired.
- **Docs.** `AGENTS.md` is self-contained (no link to a private repo), the README is a showcase,
  `docs/archive/` holds the superseded rules page and the analysis handoff, and the architecture,

## How to resume

```sh
cd rotation
git pull
git config core.hooksPath .githooks       # once per clone: pre-push gate and commit-message hook
node scripts/check.mjs                    # the one command that runs every check (about 15 seconds)
```

- `node scripts/check.mjs --e2e` adds the signed-out browser tests. `--signed-in` adds the signed-in journey
  against a local Supabase and needs Docker, `supabase start` and a freshly reset database
  (`supabase db reset`): the journey asserts on the `admin_actions` rows it creates, so a second run against
  the same database fails.
- The pre-push hook runs the same check. A push to `main` deploys to production (Vercel's Git integration).
  After a push, watch CI and the post-deploy check, then confirm `/api/health` reports the pushed commit.
- **Docker.** `supabase start` and `supabase stop` control the local stack (project id `rotation`);
  `supabase db reset` rebuilds it from the migrations and loads the demo seed. Demo accounts are
  `<name>@example.test` (Ava, Ben, Cal, Dee, Eli, Sam as admin, Fay waiting) with the local-only password
  `rotation-demo-2026`.
- **Applying a migration to production:** write the migration and its pgTAP test, prove them first inside one
  transaction that is rolled back (a script using `psycopg` with `SUPABASE_DB_URL` from `.env`, running the
  migration and the test file, then rolling back; it was not kept in the repo), then `supabase db push`
  (use `--dry-run` first), then regenerate the types **with the pinned local CLI** (`npm run db:types`, needs
  Docker), then push the code. Never print the database URL.
- **Auth settings** are changed with the Supabase Management API (`PATCH /v1/projects/<ref>/config/auth`) and
  an access token from the environment; read them back with a `GET` and print only the fields you changed.

## Traps this project has already taught us

- The **production build** catches things the type checker, lint and unit tests do not (for example a
  `"use server"` file may export only `async function` declarations). Run the build, not just the tests.
- **macOS `grep` has no `\b`.** Scrub or search for words with `grep -w`. An earlier "clean" scrub was wrong
  because of this.
- **Generated types must come from the pinned local CLI** (2.115.0). The remote generator
  (`--project-id`) is a newer version and its output fails CI's stale-types check.
- **Engine tests must pass with an empty `ROTATION_DATA_DIR`**: CI has no research cache, your laptop does.
  `scripts/check.mjs` runs them that way.
- In Playwright use **`localhost`, not `127.0.0.1`**: the auth cookie is host-specific and Next redirects to
  `localhost`. Next also has its own empty `role="alert"` element (use the `notice()` helper).
- The browser tests use port **3187** and the screenshot script port **3188**; do not start anything else on
  them.
- **The CSP carries a per-request nonce**, so every page is rendered per request. A new image host, script or
  connection must be added to the policy in `lib/security-headers.ts`, or the browser blocks it silently.
- **The database step of the check** runs only when Docker is up *and* `supabase start` has been run; if the
  stack is down it says so and skips (CI runs it anyway). Use `--require-db` to make that a failure.
- Supabase's **local** database keeps its own migration history. It went stale when the migrations were
  renamed to match production; `supabase db reset` fixes it.
- The **CI database job pulls images from a rate-limited registry** and can fail with `toomanyrequests`; the
  type-generation and `supabase start` steps retry. A re-run is safe.

## Working agreements (from the owner)

- Pushing straight to `main` is fine for this project; the gate is the local check and the hook.
- Commit subjects are `<area>: <what changed>`, no em-dash or en-dash anywhere in a message (a hook
  enforces it). Say what was and was not verified, and report failures as failures.
- Never put amounts or holdings in Discord messages, and never commit holdings, account type, secrets or
  real names. Names in fixtures and seeds are generic.
- Credentials live in the credential store and the runtime only, never in chat, commits or logs.
